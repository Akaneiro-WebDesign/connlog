## 3. 確認済み結果

### IA-PRIM-001：イベント一覧におけるユーザー間の表示分離

- 確認項目：アカウントAのイベントが、アカウントBのイベント一覧に表示されないこと
- 対象画面：`/events`
- 実施した操作：
  1. アカウントAで、A専用だと識別できるテストイベントが1件以上存在することを確認した
  2. アカウントBで`/events`を開いた
  3. Bのイベント一覧にA専用イベントが表示されないことを確認した
- 期待結果：Bのイベント一覧にAのイベントが表示されない
- 実際の結果：BにAのイベントは表示されなかった
- 判定：画面上のイベント一覧について、A・B間の表示分離を確認
- 根拠：2026年8月7日のテストアカウントA・Bによる手動確認
- 制約・未確認事項：
  - APIリクエストを直接改変した取得試験は未実施

### IA-PRIM-002：ダッシュボードにおけるユーザー間の表示分離

- 確認項目：アカウントAのイベント、タグ、メモに由来する情報が、アカウントBのダッシュボードに表示されないこと
- 対象画面：`/dashboard`
- 実施した操作：
  1. アカウントAに専用イベントが存在する状態で、アカウントBの`/dashboard`を開いた
  2. Aのイベント、タグ、メモに由来する表示がBのダッシュボードに混在しないことを確認した
- 期待結果：BのダッシュボードにA由来のデータが表示されない
- 実際の結果：BのダッシュボードにAのデータは見当たらなかった
- 判定：画面上のダッシュボードについて、A・B間の表示分離を確認
- 根拠：2026年8月7日のテストアカウントA・Bによる手動確認
- 制約・未確認事項：
  - 集計APIのリクエスト改変試験は未実施
  - 表示されないことの確認であり、全データ取得経路を網羅した結論ではない

### IA-PRIM-003：タグ・メモ更新およびイベント削除におけるユーザー間認可

- 確認項目：アカウントBが、アカウントAのタグ・メモを変更できず、イベント本体を削除できないこと
- 対象API：`PUT /api/events/update`、`DELETE /api/events/delete`
- 使用データ：Aの監査専用イベント（内部ID：`125`、外部イベントID：`401704`）
- 実施した操作：
  1. BでAの外部イベントIDを指定して更新APIを呼び出した
  2. Aでイベントを確認し、A側のタグ・メモが変更されていないことを確認した
  3. Bで作成された監査用のタグ・メモを、関連データ削除APIで削除した
  4. BでAのイベント内部IDを指定して削除APIを呼び出した
- 期待結果：BはAのタグ・メモおよびイベント本体を更新・削除できない
- 実際の結果：
  - 更新APIは`200`を返したが、A側のタグ・メモは変更されなかった
  - B側でのみ監査用タグ・メモが一時的に作成され、B自身の操作で削除できた
  - 削除APIは`404`と「イベントが見つからないか、削除権限がありません」を返し、Aのイベント本体は削除されなかった
- 判定：BによるAデータの更新・削除は確認されなかった
- 根拠：
  - 2026年8月8日のテストアカウントA・Bによる直接API呼び出しと、A画面での変更有無確認
  - `events`・`tags`・`notes`の現行RLS Policyが、各ユーザーの`user_id`と`auth.uid()`の一致を条件としていること
- 補足・改善候補：
  - 更新APIは対象イベントの所有確認を行わず、Bが所有しない外部イベントIDを指定しても`200`を返す
  - RLSによりAのデータは変更されないが、B自身のタグ・メモがイベント本体なしで作成され得る
  - 越境更新の脆弱性ではない。一方で、APIの応答整合性と孤立した関連データの防止のため、MVP後の低優先度改善候補とする

### IA-PRIM-004：RLS Policyと実地テスト結果の照合

- 確認項目：`events`・`tags`・`notes`の現行RLS Policyが、テストアカウント間のデータ分離と整合すること
- 実施した操作：Supabase SQL Editorで`pg_policies`を参照し、各テーブルのPolicy条件を確認した
- 実際の結果：
  - `events`はSELECT・INSERT・UPDATE・DELETEの各操作で、`auth.uid() = user_id`を条件としている
  - `tags`はSELECT・INSERT・UPDATE・DELETEの各操作で、`auth.uid() = user_id`を条件としている
  - `notes`も本人の`user_id`に限定するPolicyが設定されている
- 判定：今回の表示分離および更新・削除拒否の実地テスト結果と、RLS Policyの方向性は整合している
- 制約・未確認事項：
  - 全API・全クエリ経路を網羅する検証ではない
  - `notes`には同じ目的のPolicyが複数存在するため、MVP後に不要Policyの整理を検討する

## 4. 現時点のまとめ

テストアカウントA・Bを用いた通常画面の確認では、次の表示分離を確認した。

- Bのイベント一覧にAのテストイベントは表示されない
- BのダッシュボードにA由来の情報は見当たらない
- BによるAのイベント本体の削除は`404`で拒否された
- BがAの外部イベントIDを指定しても、A側のタグ・メモは変更されなかった

ただし、これは通常画面操作、限定的な直接API呼び出し、およびRLS Policy参照による確認結果である。全API・全データ取得経路、DB関数・権限などの確認は継続して実施する。
