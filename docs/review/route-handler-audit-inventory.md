# Route Handler監査台帳

最終更新：2026年8月5日

## 目的

MVP公開前の独立セキュリティ監査に向け、ConnLog内の全Route Handlerについて、静的確認の結果と実地確認が必要な項目を記録する。

この台帳は静的確認の記録であり、認証・認可・RLS・エラー応答の最終判定は、`docs/review/independent-security-audit-test-spec.md` に沿った実地テストで行う。

## 対象と確認方法

対象は、`src/app` 配下の`route.ts` 9ファイル・10メソッド。

* Route Handler内で`supabase.auth.getUser()`による認証確認を行っているか
* 操作対象をログイン中の`user.id`に限定しているか
* リクエスト入力を必要な範囲で検証しているか
* service role keyの使用箇所がサーバー側に限定されているか
* 実地監査で追加確認すべき事項は何か

## middlewareの位置付け

`middleware.ts`は、静的ファイル等を除くほぼ全リクエストに適用される。

middleware内の`supabase.auth.getUser()`は、SupabaseセッションCookieの更新を担う。一方で、未認証利用者をログイン画面へリダイレクトする処理や、APIへ401を返す処理は持たない。

したがって、APIの認証強制はmiddlewareに依存せず、各Route Handler内での`auth.getUser()`確認を根拠とする。

## Route Handler一覧

| パス                    | メソッド   | 用途                    | 静的確認結果                                                                                                               | 実地監査での確認項目                                                          |
| --------------------- | ------ | --------------------- | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `/auth/confirm`       | GET    | 招待メールのOTP検証           | `token_hash`と`type=invite`を確認する。不正時・OTP検証失敗時は`/login`へリダイレクトする。`next`は`/`で始まり`//`で始まらない内部パスだけを許可し、`origin`を前置して遷移する。 | 不正な`next`、不正なトークン、招待以外の`type`で外部サイトへ遷移しないこと。                        |
| `/auth/callback`      | GET    | OAuth／認証コードのセッション交換   | `code`を`exchangeCodeForSession`へ渡し、成功時だけ安全化した内部`next`へ遷移する。失敗時は`/login`へリダイレクトする。                                    | 不正な`next`、不正な`code`で外部リダイレクトや意図しないログイン状態にならないこと。                    |
| `/api/search-event`   | GET    | connpassイベント検索        | Handler内で`auth.getUser()`を実行し、未認証時は401。`event_id`は数字のみ許可する。connpass API keyはサーバー環境変数からのみ取得する。                        | 未認証時の401、異常な`event_id`の400、外部API障害時の502、レスポンスにAPI key等が含まれないこと。     |
| `/api/search-user`    | GET    | connpassユーザーの参加イベント検索 | Handler内で認証確認を行い、未認証時は401。`nickname`の空値・長さ、`start`、`count`を検証する。`count`は最大100に制限する。                                  | 未認証時の401、境界値・不正値の400、外部API障害時の502、過大なリクエストを受け付けないこと。                |
| `/api/profile`        | GET    | プロフィール取得              | Handler内で認証確認を行い、取得対象をログイン中の`user.id`に限定する。                                                                          | 未認証時の401、別ユーザーのプロフィールを取得できないこと。                                     |
| `/api/profile`        | PUT    | プロフィール更新              | Handler内で認証確認を行い、更新・新規作成の対象をログイン中の`user.id`に固定する。表示名・自己紹介に長さ制限を設ける。                                                  | 未認証時の401、別ユーザーのプロフィールを更新できないこと、境界値・不正入力の扱い。                         |
| `/api/events/update`  | PUT    | イベントに紐づくタグ・メモの更新      | Handler内で認証確認を行う。タグ・メモの削除条件および新規保存時の`user_id`をログイン中の`user.id`に限定する。                                                  | 未認証時の401、他ユーザーのイベント・タグ・メモを変更できないこと、入力形式・長さの境界値、DBエラー詳細が利用者へ露出しないこと。 |
| `/api/events/delete`  | DELETE | イベントと関連データの削除         | Handler内で認証確認を行う。イベント削除を`id`と`user_id = user.id`で限定し、関連タグ・メモも`user_id`で限定する。                                         | 未認証時の401、他ユーザーのイベントや関連データを削除できないこと、DBエラー詳細が利用者へ露出しないこと。             |
| `/api/account/delete` | DELETE | アカウント削除               | Handlerでログイン中ユーザーを確認し、削除対象はその`user.id`のみとする。service role keyはサーバー側Route Handler内でのみ使用する。                             | 未認証時の401、別ユーザーを削除できないこと、削除完了後にログイン・データ取得ができないこと、途中失敗時の部分削除の扱い。      |
| `/api/dashboard-data` | POST   | ダッシュボード用データ取得         | Handler内で認証確認を行う。`events`、`notes`、`tags`の取得をすべて`user_id = user.id`で限定する。                                             | 未認証時の401、他ユーザーの集計・イベント・タグ・メモが含まれないこと、DBエラー詳細が利用者へ露出しないこと。           |

## 静的確認で実地監査へ引き継ぐ項目

* `/api/events/update`、`/api/events/delete`、`/api/dashboard-data`で、DBエラーの詳細がレスポンスへ含まれないこと
* `/api/events/update`の`event_id`、タグ、メモに対する入力値検証が十分か
* RLSを含め、別ユーザーのデータを取得・更新・削除できないこと
* `/api/account/delete`で途中失敗した場合の部分削除が、利用者にとって問題となる状態を残さないこと
* 検索APIへのレート制限は未実装のため、公開範囲と想定利用量に対して追加対策が必要か
