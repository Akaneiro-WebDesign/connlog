# ConnLog Astra独立セキュリティ再監査記録

作成日：2026年9月18日
監査実施日：2026年9月17日

## 1. 目的

この文書は、ConnLogの少人数テストユーザー募集前に、現在の実装へCritical・High相当の問題が残っていないか、Astraを使用して独立した静的セキュリティ監査を行った結果を記録するものである。

過去に実施した自己点検や独立監査の結論を前提とせず、最初に現行コードを確認し、その後で既存の監査・QA記録と照合した。

## 2. 監査対象

- ブランチ：`main`
- 基準コミット：`5fe3a84619ec876cba4cb2c0a77f1cfe5e7e0320`
- 監査方法：リポジトリ内のコード、設定、DB関連SQL、依存関係、既存文書を対象とした静的監査
- ファイル変更：なし
- 外部サービスへの通信：なし
- Production、Supabase、Vercel、connpass APIへのアクセス：なし
- `.env.local`などの秘密情報ファイル：確認対象外

主な確認領域は次のとおり。

- 認証、招待、セッション管理
- Route Handlerの本人確認と認可
- Supabase RLSとDB制約
- `service role key`の利用範囲
- イベント、タグ、メモの保存・更新・削除
- プロフィール更新
- アカウント削除
- リダイレクト先の検証
- 入力値検証
- Next.jsのサーバー・クライアント境界
- 秘密情報とAPIエラーの露出
- 依存パッケージ

## 3. 結論

今回の静的監査では、攻撃成立を確定できるCritical・High相当の問題は確認されなかった。

少人数のテストユーザー招待を一律に停止すべき、確定した認証回避、他ユーザーへの越権操作、データ漏えいも確認されなかった。

一方、招待前の改善を推奨する項目として、次の4件が確認された。

| ID | 内容                                    | 深刻度    | 分類               |
| -- | ------------------------------------- | ------ | ---------------- |
| F1 | 外部由来HTMLをテキスト化する処理で`innerHTML`を使用している | Medium | XSSにつながる可能性のある構造 |
| F2 | 複数の保存・削除処理が一体化されておらず、途中失敗時に不整合が残り得る   | Medium | データ整合性・信頼性       |
| F3 | 本人が所有していないイベントIDへ、本人名義の孤立タグ・メモを作成できる  | Low    | データ整合性・API応答     |
| F4 | 不正なプロフィール入力を空欄への正常更新として処理する           | Low    | 入力値検証・本人データ消失    |

これらは、今回の監査範囲で他ユーザーへの越権操作や情報漏えいが成立すると確認された問題ではない。

## 4. 確認された指摘

### F1. イベント説明文のテキスト化

対象：

- `src/lib/sanitizeEventDescription.ts`
- `src/components/EventSearchForm.tsx`
- `src/components/SearchTagMemoModal.tsx`
- `next.config.ts`

イベント説明文をテキスト化する際、ブラウザ上で作成した要素の`innerHTML`へ外部由来の文字列を代入し、`textContent`を取り出している。

最終的にReactへ渡す文字列はエスケープされるが、HTMLを解析する段階でイベント属性などの副作用が起こる可能性が指摘された。

第三者が悪意あるHTMLをconnpass経由で別の利用者へ配信できるか、現在の処理で実際にスクリプトが実行されるかは、今回の静的監査では確認していない。

招待前に、実行可能なDOMへ外部由来HTMLを設定しないテキスト化処理へ変更し、外部通信を行わないテスト用HTMLで確認する。

### F2. 保存・削除処理の途中失敗

対象：

- `src/app/api/events/update/route.ts`
- `src/lib/saveEventWithTagsAndNote.ts`
- `src/app/api/events/delete/route.ts`
- `src/app/api/account/delete/route.ts`

イベント、タグ、メモの保存・更新・削除は、複数のDB操作に分かれている。先行処理の成功後に後続処理が失敗した場合、旧データの消失、不完全な保存、成功表示と実データの不一致が起こる可能性がある。

また、イベント保存処理には、タグ削除の失敗をログへ記録した後も後続処理を続行する経路が確認された。

対応は次の2段階に分ける。

1. 削除や更新に失敗した場合、成功扱いで後続処理を続けない
2. イベント、タグ、メモの一連の処理をDBトランザクションへまとめる設計を検討する

アカウント削除の部分失敗については、既知の信頼性上の課題として公開後の改善候補とする判断も可能とされた。

### F3. 孤立したタグ・メモの作成

対象：

- `src/app/api/events/update/route.ts`
- `docs/db/2026-07-14-fix-events-tags-rls-ownership.sql`

更新APIは、入力された`event_id`に対応するイベントを本人が所有しているか確認せず、認証済みユーザー本人の`user_id`を使用してタグとメモを更新する。

このため、本人のイベント本体が存在しないIDを指定した場合でも、本人名義のタグやメモを作成して`200`を返す構造が残っている。

他ユーザーのイベントや関連データは変更されないため、越権操作や情報漏えいとは判断しない。

最初の書き込みより前に、`events`を`user_id`と`event_id`の組み合わせで照会し、本人のイベントが存在しない場合は`404`を返して後続処理を行わない修正を検討する。

### F4. プロフィールAPIの入力値検証

対象：

- `src/app/api/profile/route.ts`

不正なJSON、項目の欠落、文字列以外の値を空文字へ変換し、表示名や自己紹介の削除として正常に保存する経路が確認された。

これは他ユーザーへの影響ではないが、認証済みユーザー本人のプロフィールが意図せず消える可能性がある。

リクエスト本体と各フィールドの型を検証し、不正な入力は`400`としてデータを変更しない処理へ変更することを検討する。

## 5. 問題が確認されなかった主な領域

今回の監査範囲では、次の領域に新たな問題は確認されなかった。

- 指定された主要APIには`getUser()`による本人確認がある
- データの所有者はリクエストから受け取った`user_id`ではなく、認証済みユーザーから決定している
- `service role key`はアカウント削除Routeに限定され、ブラウザへ渡す経路は確認されなかった
- `events`と`tags`のRLSはSQL上、本人のCRUDに限定されている
- `events(user_id, event_id)`のUNIQUE制約は、利用者ごとに同じconnpassイベントを保存できる仕様と整合している
- 認証用の`next`パラメータから外部サイトへ遷移する構造は確認されなかった
- 利用者データを共有キャッシュや静的生成へ格納する実装は確認されなかった
- APIレスポンスからDBエラーや秘密情報を直接返す実装は確認されなかった
- 過去に修正済みとした主要な問題の再発は確認されなかった

`notes`、`users`、DB関数、Productionの現在の設定については、リポジトリだけでは現在状態を確定できない。既存の実地確認以降に設定変更がある場合は、その差分を確認する。

## 6. 既存監査との照合

既存監査との照合では、次の結果となった。

- F3の孤立タグ・メモは、過去の実地確認と一致する未修正の継続事項
- 退会処理の部分失敗と検索APIのレート制限不足は、既存記録と一致
- タグ・メモの入力上限、APIエラー詳細、URLスキーム検証、削除ID検証は現在のコードで対応済み
- アカウント削除時の再認証、認証callbackの遷移先検証、パスワード最低8文字は対応済みの状態を維持
- 過去に修正済みとした問題の再発は確認されなかった
- F1、通常保存・編集時の途中失敗、F4は今回の監査で新たに具体化された

## 8. 対応方針

今後は、次の順番を目安に個別のブランチとPRで対応する。

1. F1：イベント説明文の安全なテキスト化
2. F3：更新APIでの親イベント確認
3. F4：プロフィールAPIの入力値検証
4. F2前半：削除失敗後も処理を続行する経路の修正
5. F2後半：イベント、タグ、メモ保存のトランザクション化
6. 既存依存監査以降の脆弱性情報の差分確認

F1、F3、F4は、それぞれ独立したPRとして対応する。

F2のトランザクション化は、DB関数、RLS、実行権限、`search_path`、既存データとの整合性を含む設計が必要なため、他の小規模修正と分けて扱う。

## 9. 最終判断

今回の監査では、少人数テストユーザーの招待を直ちに中止すべき確定的な問題は確認されなかった。

一方、F1からF4は、安全性とデータ整合性を改善する具体的な課題として記録し、各項目の影響と修正範囲を確認しながら対応する。

この判断は、監査対象コミットと既存のProduction・Supabase確認記録の範囲に基づくものであり、将来の設定変更や依存パッケージ更新後も無条件に安全性を保証するものではない。
