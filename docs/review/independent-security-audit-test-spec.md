# ConnLog 独立セキュリティ監査 テスト仕様書

作成日：2026年8月4日
目的：MVP公開前の独立した一次セキュリティ監査に用いるテスト仕様
状態：監査手順・報告形式の定義。監査結果や安全性の結論は含めない。

## 1. 監査の目的

ConnLogのMVP公開前に、認証、認可、データ分離、API、データベース権限、秘密情報の取り扱い、依存関係および基本的なセキュリティ設定について、ソースコードと許可されたテスト環境を用いて独立に確認する。

監査者は、既存の調査結果や結論に影響されず、確認できた事実と根拠に基づいて評価する。

## 2. 監査の区分

### 一次監査

一次監査では、次の対象を中心に確認する。

- アプリケーションのソースコード
- Next.js、Vercelなどの設定ファイル
- Supabaseのmigration、SQL、DB関数・権限に関する定義
- `package.json`、lockfileなどの依存関係定義
- このテスト仕様書
- 明示的に許可されたローカル環境またはPreview環境

一次監査では、既存の安全性調査・監査結果・ZAPレポートを参照しない。既存の結論に引っ張られず、独立した評価を行うためである。

### 二次比較

一次監査の報告が確定した後に、既存の調査文書やOWASP ZAPレポートを参照し、指摘・未確認事項・対応方針に差異がないか比較する。

二次比較は、一次監査の結論を変更するためではなく、確認漏れや判断の相違を整理するために行う。

## 3. 一次監査の対象

### アプリケーションと設定

- `src`配下など、アプリケーションの実装コード
- API Route Handler
- 認証コールバック、middleware、リダイレクト処理
- Next.js設定、Vercel設定、公開ヘッダー設定
- Supabaseクライアント、サーバー側処理、認証・認可処理
- 環境変数名の参照箇所
  - 値そのものや秘密情報は対象外とする
- `package.json`、lockfile、依存関係のバージョン
- DB schema、migration、SQL、DB関数、RLSポリシー、権限定義

### 機能・データ

- 招待制ユーザー登録
- 招待メールからの初回パスワード設定
- ログイン・ログアウト
- 認証コールバックとリダイレクト先の制限
- connpassイベントの検索・登録
- イベント履歴の編集・削除
- タグ・メモの保存
- ダッシュボード・スキル分析
- プロフィール編集
- パスワード変更
- アカウント削除
- `users`、`events`、`tags`、`notes`のデータアクセス制御

### テストデータ

データを伴う確認は、監査用に用意された2つのテストアカウントと、そのアカウントに紐づくテストデータだけを使用する。

実ユーザー、実ユーザーのイベント履歴、実ユーザーのプロフィール情報は確認対象に含めない。

## 4. 一次監査で参照しないもの

以下は、一次監査の結論が確定するまで参照しない。

- この仕様書以外の`docs/review`配下の既存調査・監査文書
- `zap-reports`配下のレポート
- OWASP ZAPの警告に対する既存の評価・対応方針
- Codexその他のAI、人間による過去の監査メモ
- `.env`、`.env.local`などの秘密情報ファイル
- APIキー、トークン、Cookie、認証情報、DBバックアップ
- 実ユーザーのデータを含むファイル・ログ・エクスポート

## 5. 許可する環境と操作

### 許可する環境

- 監査者のローカル開発環境
- 明示的に許可されたVercel Preview環境
- テストアカウントとテストデータのみを使用するSupabase環境

Production環境は一次監査の対象外とする。通常のブラウザ確認を含め、Production環境へのアクセスは明示的な許可がある場合だけ行う。

### 許可する操作

- ソースコード、設定、migration、依存関係定義の静的確認
- ローカル環境または許可されたPreview環境での通常操作
- テストアカウントを用いたログイン・ログアウト
- テストデータの作成、編集、削除
- 2つのテストアカウント間でのアクセス制御確認
- 認証済み・未認証状態でのAPI応答の確認
- ID、`user_id`、リクエストボディ、URLパラメータの改ざんに対する拒否の確認
- 依存関係の既知脆弱性情報の確認
- HTTPレスポンスヘッダーの確認

## 6. 禁止する操作

以下の操作は禁止する。

- Production環境へのActive Scan
- 負荷試験、DoS試験、大量リクエスト
- 外部サービス、connpass API、Supabase、Vercel、GitHubなどへのスキャン
- ブルートフォース、パスワード総当たり、トークン推測
- 汎用的な攻撃コード、マルウェア、侵入補助コードの作成
- 実ユーザーデータを使った検証
- `.env`、APIキー、トークン、Cookie、認証情報の読み取り・出力・共有
- 許可されていない環境、アカウント、URLへのアクセス
- ソースコード、設定、Supabase、Vercel、GitHubなどの変更
- migrationの適用、DB関数・RLS・権限の変更
- commit、push、PR作成、デプロイ
- 発見した問題を利用してデータを取得・変更・削除すること

疑わしい挙動を発見した場合は、影響を最小限にした再現確認までに留め、それ以上の検証は実施者へ相談する。

## 7. 確認観点

### 7-1. 認証と招待フロー

以下を確認する。

- 招待または許可された手段を経ない一般ユーザー登録が可能になっていないか
- 招待メールからの初回パスワード設定が想定した利用者に限定されるか
- ログイン・ログアウトの状態遷移が適切か
- パスワード変更時に適切な認証状態が求められるか
- 認証コールバックのリダイレクト先が安全なパスに制限されるか
- 外部URLや想定外のパスへのリダイレクトが許容されないか
- 未認証状態で保護対象の画面・操作に到達できないか

### 7-2. API Route Handlerの認証・認可

各API Route Handlerについて、少なくとも以下を確認する。

- リクエストごとに認証済みユーザーを適切に取得しているか
- 未認証リクエストが拒否されるか
- 他ユーザーのID、`user_id`、イベントID、タグID、メモIDなどを指定しても操作できないか
- クライアントから渡された所有者情報を無条件に信用していないか
- 入力値の型・必須項目・形式が適切に確認されているか
- エラー応答が不要な内部情報や秘密情報を含まないか
- 更新・削除・アカウント削除に必要な認可が確認されているか

### 7-3. RLSとデータ分離

`users`、`events`、`tags`、`notes`について、RLSとアプリケーション側のアクセス制御が整合しているか確認する。

2つのテストアカウントを用い、少なくとも以下を確認する。

- アカウントAのデータをアカウントBが一覧・取得できないか
- アカウントAのデータをアカウントBが更新・削除できないか
- 新規作成時に、作成者・所有者がリクエストの利用者と適切に関連付けられるか
- URL、フォーム、リクエストボディのIDや`user_id`を改ざんしても、他者データへアクセスできないか
- DB関数を経由する操作でも、必要な権限確認が維持されているか

### 7-4. service role keyと秘密情報

以下を確認する。

- service role keyを使用する処理と、その必要性
- service role keyを使うコードがサーバー側に限定されているか
- クライアント側のバンドル、公開環境変数、レスポンス、ログにservice role keyが露出しない設計か
- 秘密情報を含む実値を読み取らずに、参照箇所と公開範囲を確認できるか

### 7-5. アカウント削除

以下を確認する。

- 削除処理が認証済み本人に限定されているか
- 他ユーザーを指定して削除できないか
- service role keyを用いる場合、その利用範囲が最小限か
- 削除対象のデータと、削除後のセッション・画面遷移が意図した仕様と一致するか
- 失敗時に不整合や不要な情報露出が起きないか

### 7-6. DB関数・権限・migration

以下を確認する。

- migrationに意図しない権限付与、RLS無効化、過度な公開設定がないか
- DB関数の実行権限、`SECURITY DEFINER`の利用、`search_path`などの設定が適切か
- DB関数が呼び出し元の権限や利用者識別を不適切に回避していないか
- schema、関数、テーブルへの権限が最小限か
- 現在の実装とmigration・SQL定義に矛盾がないか

### 7-7. 依存関係と設定

以下を確認する。

- 依存関係に既知の重大な脆弱性がないか
- 脆弱性が報告されている場合、実際に到達可能なコードパスか
- Next.js、React、Supabase関連パッケージ、認証・HTTP関連パッケージの更新状況
- セキュリティヘッダーがアプリケーション設定どおりに返却されるか
- CSP、クリックジャッキング対策、MIME sniffing対策、Referrer Policy、Permissions Policyなどが必要な範囲で設定されているか

### 7-8. 個人情報とログ

以下を確認する。

- 実ユーザーのメールアドレス、プロフィール、イベント履歴、トークンなどを監査報告へ含めないこと
- 画面・API・エラーログに不要な個人情報や秘密情報が含まれないこと
- 報告で例示が必要な場合、テストデータまたは伏せ字を使用すること

## 8. 指摘の報告形式

指摘ごとに、少なくとも以下を記載する。

    識別子：
    タイトル：
    重大度：Critical / High / Medium / Low / Informational
    対象箇所：
    確認済み事実：
    推測・未確認事項：
    根拠：
    再現条件：
    必要な攻撃条件：
    影響範囲：
    確信度：高 / 中 / 低
    誤検知の可能性：
    MVP公開前の対応必要性：必須 / 推奨 / 後続検討 / 対応不要
    推奨対応：

根拠には、可能な限り次を明記する。

- 該当ファイルと行・関数・設定項目
- 実行したコマンド
- テストしたリクエスト・操作
- 期待結果と実際の結果
- 制約により確認できなかった事項

「確認済み事実」と「推測・未確認事項」を混在させない。再現できていない指摘は、再現済みの問題として扱わない。

## 9. 重大度の目安

- Critical：秘密情報の露出、認証回避、多数または全ユーザーのデータへの重大な不正アクセスなど、直ちに公開を止めるべき問題
- High：他ユーザーのデータ取得・更新・削除、権限昇格、本人以外のアカウント削除など、MVP公開前の対応を強く要する問題
- Medium：成立条件や影響が限定されるが、公開前または早期の対応判断が必要な問題
- Low：影響が小さい設定上の改善点、限定的な情報露出など
- Informational：直ちに脆弱性とはいえない確認事項、改善候補、設計上の留意点

重大度は警告件数やツール上の表示だけで決めず、再現性、攻撃条件、影響範囲、既存の防御策を踏まえて判断する。

## 10. 監査の完了条件

一次監査は、以下を満たした時点で完了とする。

- 対象範囲のソースコード・設定・migration・依存関係を確認した
- 認証、API認可、RLS、2アカウント間のデータ分離、service role key、アカウント削除を確認した、または確認不能な理由を記録した
- 禁止操作を実施していない
- 指摘、未確認事項、問題なしと判断した観点を区別して報告した
- 各指摘に根拠、再現条件、攻撃条件、影響範囲、確信度、誤検知の可能性、MVP公開前の対応必要性を記載した
- 監査中に変更、commit、push、環境設定変更をしていない

一次監査報告の確定後にのみ、既存の調査文書・ZAPレポートとの二次比較へ進む。
